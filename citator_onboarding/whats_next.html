What’s next

The two pipeline configurations evaluated to date (see Experiments) are the working artifacts. This page is the wrap-up: why the architecture looks the way it does, what’s still hard, and what we’re actively working on to move the project forward.

Why we don’t just use eyecite

The natural question: FLP already maintains eyecite, an open-source rule-based citation parser. If eyecite already finds citations, why do we still need an LLM to extract them?

Eyecite’s purpose is citation extraction and grouping — locating citation strings in legal text and linking all references to the same case (full citations, parallel citations, short forms like 489 U.S., at 318, Id., supra, and case-name references) into a single chain. That is exactly the foundation the citator needs before it can label treatment. We use eyecite during preprocessing to pre-tag citation spans with <citedCase> markers that the downstream stages consume.

Where eyecite is solid: deterministic citation grammar on clean, canonical text — volume / reporter / page tuples for modern federal reporters, recognized short-form patterns when the chain is short and unambiguous. Where it falls short for our extraction task:

Failure mode

Short references and case-name chains

A single cited case usually appears as a full citation followed by a long tail of short forms: Id. citations, supra references, “in Parker”, “as seen in Parker”, “the Parker Court”. Eyecite’s chain resolver can lose these references — especially when many citations sit between the full cite and the short form, or when two cases in the opinion share part of a name. The case ends up split across records, or the short form attaches to the wrong case.

Failure mode

OCR-mangled citations

Opinion text often comes from OCR of PDFs or older scans. A reporter abbreviation like F. Supp. rendered as F, Supp. (comma instead of period), a volume number split across a line break, or trial-court line numbers interleaved with the text — any of these break eyecite’s deterministic patterns. The citation goes unmatched, or the resolver chains it to the wrong case downstream.

Failure mode

Implicit case references

Some references to a previously-cited case carry no citation string at all: “the prior decision in this matter”, “as we held last term”, “the dissent”. Eyecite has nothing to pattern-match. An LLM reading the surrounding context can recognize these and attach them to the right cited-case record.

An LLM-driven extraction stage compensates by reading citations in context: it can resolve a case-name reference back to its earlier full citation even when eyecite drops the link, recover citations OCR has mangled into a form eyecite’s regex can’t match, and pick up implicit references that carry no citation string at all. The downstream classifier then operates on a clean, deduplicated list of cited cases.

The open pain points

1 · Fuzzy, subjective labels

Treatment is interpretive — at the margins, even experts can disagree (did a case “Limit” an earlier holding, or merely “Distinguish” it?). That grey zone caps consistent labeling and fair evaluation.

2 · Skewed data & misleading metrics

~94% of benchmark labels are the neutral “Cited by.” Top-line numbers (accuracy, weighted F1) inflate under that skew and hide the rare classes — exactly the high-value signal. We lean on macro F1 + QWK together; the long-tail zeros on the rare classes are where the real ceiling sits.

3 · Scarce evaluation data

The treatments that matter are genuinely rare in the corpus, and 13 of 43 taxonomy variants don’t appear in the benchmark at all. Without enough labeled examples per class, the rare-class metrics aren’t stable enough to identify real gaps.

4 · Citation extraction is hard

Eyecite alone misses chained references, supra cites, and implicit case mentions; the LLM extraction stage catches most of these but not all. Missed or mischained refs propagate into the classifier as wrong or missing cited cases.

5 · Messy source text

OCR errors, missing paragraph breaks, NBSP encoding, trial-court line-number noise, duplicate opinion records. Wrong section bounds in extraction cascade into wrong context in classification.

6 · Context loss on long opinions

Very long opinions exceed model context and get paginated. Citation chains across page boundaries (an Id. on page 2 referring back to a full cite on page 1) lose their link. Pagination is a working measure, but it caps quality on the largest opinions.

Production cost outlook

Quality is one axis; cost is the other. At corpus scale (millions of opinions), an LLM-driven citator gets expensive fast. The model below decomposes per-run cost into a variable rate (scales with how much opinion text the system has to ingest and emit) and a fixed per-case cost (prompt overhead per call + downstream stage costs that don’t track opinion size), so any candidate setup can be projected against a realistic workload.

The decomposed cost model

total cost ≈ A × (opinion-text tokens, in millions)  +  B × (cases)

  • A — variable rate per 1M opinion-text tokens (model input rate + output amortized to opinion volume).
  • B — fixed cost per case. Mostly prompt overhead per call; for the two-stage pipeline it also bundles the classification stage’s per-cited-case cost.

A is ~9× lower for Haiku + Kimi — the per-token work is done by cheaper models. B is ~3.3× higher for Haiku + Kimi — the classification stage makes ~10.75 calls per cluster, which compounds in B independent of opinion size. Sonnet 1-stage trades a higher A for a much lower B.

Cost crossover: ~6,500 opinion-text tokens per case

Above this opinion size, Haiku + Kimi is the cheaper pipeline. Majority opinions in production will almost always run larger than this threshold (the benchmark’s opinions already average ~16,700 tokens), so the Haiku + Kimi cost advantage holds for most real workloads.

Caveats worth flagging

  • Prompt caching would slash B. Bedrock batch doesn’t currently support prompt caching. If it did, cache reads at ~10% of input rate would drop Sonnet’s B from $0.012 to ~$0.001 — about a 12× reduction on the fixed overhead. The crossover would shift dramatically and Sonnet 1-stage would become cost-competitive on most opinion sizes.
  • Cited-case density swings B for the 2-stage pipeline. The classification stage fires per cited case (~10.75 on this benchmark). An opinion with twice as many cited cases roughly doubles B for Haiku + Kimi; Sonnet 1-stage is robust to that since it does one call per page.
  • Pagination amplifies B for the 1-stage pipeline. Prompt overhead is paid per page, not per case. Only 3 of 383 clusters paginated on the benchmark. A workload of very large opinions (paginating 3–5×) would multiply Sonnet’s B roughly proportionally.
  • Latency is unpriced. Batch SLA is hours; on-demand is real-time at ~2× the cost. Any tier that needs real-time inference should be modeled on-demand — not from these batch numbers.
  • Per-court variation isn’t modeled. Different jurisdictions have very different opinion-size distributions and cited-case densities. Per-court A and B would give more accurate planning for any non-uniform production traffic mix.

What’s already in motion & upcoming opportunities

Pipeline-side workstreams only. For benchmark-side workstreams, see The Benchmark → What’s in motion.

Already in motion

  • Failure-mode analysis. Systematically reviewing where the pipeline gets wrong predictions on the benchmark — categorizing error types, surfacing patterns, and feeding each finding into the next round of prompt and design changes.
  • Expert outreach for prompt help. Domain experts are being consulted on the specific error axes the model gets wrong (cert. denials, “as recognized by” constructions, partial dispositions) to shape the next round of prompt iteration.
  • Split disposition from citing reference. Architectural experiment: classify Direct-History disposition (what the appellate court did to the case below) and Citing Reference treatments with separate prompts and evaluations. Skipping Related Reference for the first pass to keep it tractable. Will surface where a single-prompt approach bottlenecks.
  • New annotation app for experts. A replacement for the current expert-annotation workflow, with the goal to accelerate benchmark growth and rare-class coverage by removing friction from the labeling process itself.
  • Citation-extraction validation pass. A hand-annotation effort on the extraction step — did the pipeline find every cited case with the right scope? Provides the clean-citation set we need to evaluate the classifier on its own, separating the two tasks (citation extraction and treatment classification).
  • Demo site. A static citator demo over a curated set of cases, showing actual predictions from today’s pipeline so experts can judge prediction quality and flag failure modes — alongside stakeholder review and end-to-end UX validation.

Upcoming and future opportunities

  • Per-court F1 breakdown. Disaggregating headline metrics by court bucket so we can tell corpus-breadth issues (the pipeline hasn’t seen enough state-court language) from genuine model issues.
  • Case-summary-augmented snippets. Add a short summary of each cited case as extra context to the classifier’s input. Treatment is sometimes implicit in what the cited case stood for — knowing case X is a procedural-default ruling makes “abrogated by” more recognizable than reading the snippet alone.
  • Upstream text-quality work. OCR / markup / paragraph-structure problems sit beneath every other failure mode. A categorized text-quality gap analysis — what fails, where, how much — would tell us how much of the macro F1 ceiling is text-quality vs model capability.
  • Cross-court prompt tuning. The benchmark’s federal-appellate weighting means the pipeline is best on the language it’s tuned for. Prompts tuned on cross-court reporter and disposition language are needed alongside benchmark coverage expansion.
