Haiku + Kimi (2-stage)

Haiku 4.5 + Kimi K2.5, two-stage. Each model does what it’s best at — Haiku finds the cited cases (cheap, locally faithful), Kimi classifies them (best treatment F1 from the bake-off). The cost baseline subsequent experiments measure against — roughly half the per-case cost of single-stage Sonnet, at the price of weaker agreement on the rare classes.

Architecture

Stage 1 · Extract

Haiku 4.5 — find cited cases

  • Walk the opinion text in reading order (lead → concurrence → dissent)
  • Identify each cited case and the textual region the citation applies to
  • Group repeated mentions (full cite + Id. + supra + short forms) into one case
  • Output: one record per (citing, cited) pair, anchored to character offsets
→
Stage 2 · Classify

Kimi K2.5 — assign treatment

  • Read the textual region around each citation — not the whole opinion
  • Pick a label from the 43-treatment taxonomy
  • Anchor the label to a verbatim quote from the opinion (no quote, no label)
  • Emit a 1–2 sentence rationale connecting the quote to the assigned treatment
  • Output: treatment + quote + rationale per cited case
→
Stage 3 · Post-process

Canonicalize + derive severity and direction

  • Canonicalize the LLM’s free-text treatment against the 43-treatment taxonomy
  • Look up severity and direction from the canonical treatment
  • Per-case rollup: most-negative inbound, most-recent-negative
  • Output: the same downstream shape used by all consumers

Everything the model emits is anchored to source text. Predictions that don’t anchor are discarded — the main guard against hallucinated citations or treatments.

Why this configuration

The motivation was cost. Earlier small-set runs in Phase 4 had shown this two-stage configuration matching single-stage Sonnet on treatment quality at roughly half the cost — strong enough to warrant a full-benchmark eval. The model pairing itself came out of the Phase 3 17-model bake-off (see Experiments): Haiku 4.5 was decent at extraction completeness (small misses, fewer fragmentations than other cheap models), and Kimi K2.5 produced the best F1 on the negative-treatment flag (0.70, beating Sonnet’s 0.63 at the time). Each model does only what it’s best at.

On the full benchmark, this two-stage configuration set the baseline that subsequent experiments measure against. Single-stage Sonnet has since beaten it on every agreement metric — the comparable-quality claim from the small-set runs didn’t hold up at scale. The cost argument is intact, though — this configuration is roughly half the per-case cost of single-stage Sonnet, so it remains the default for cost-sensitive corpus-scale runs where the quality gap is acceptable.

Where it shines

Strengths

  • Cost. Roughly half the per-case cost of single-stage Sonnet. The obvious default when crawling whole jurisdictions or expanding benchmark coverage at scale.
  • Focused classifier. Stage 2 reads only the section around each citation, not the whole opinion — cheaper, faster, and easier to iterate on the classifier prompt independently.
  • Independent stage iteration. Extraction and classification can be tuned separately, which made the bake-off-driven model pairing possible in the first place.

Where it struggles

Weaknesses

  • Loses to single-stage Sonnet everywhere on the latest comparison. Direct History, Citing Reference, treatment macro F1, QWK, and κ all favour the revised-prompt Sonnet run. The original “wins on Citing Reference” advantage that motivated this configuration is now gone.
  • Direct History. Loses to single-stage Sonnet on appellate-disposition treatments by a wide margin. Splitting extraction and classification loses the holistic view of the appellate posture that single-pass keeps.
  • Inter-stage cascade. When Stage 1 mis-bounds a section, Stage 2 reads the wrong context and the treatment goes wrong — a class of error that single-stage Sonnet can’t produce.
  • Long-tail rare classes. Like every configuration tested so far, struggles on the rare treatments at the bottom of the distribution. Driven primarily by benchmark scarcity, not model capability.
